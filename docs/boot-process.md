# MVentX Boot Process Specification

This document details the complete boot lifecycle of a computer booting from an MVentX-prepared USB drive, along with the Milestone 1 prototype implementation.

---

## 1. Boot Stages Overview

```
[Target Computer Power-On]
         │
         ▼
[UEFI Firmware POST]
         │
         ▼
[Detects Partition 1: MVX_BOOT (ESP FAT32)]
         │
         ▼
[Loads /EFI/BOOT/BOOTX64.EFI (GRUB 2)]
         │
         ▼
[GRUB 2 Core Initialization]
 - Loads essential modules (part_gpt, part_msdos, fat, exfat, configfile)
 - Sets root to (hdX,1) [MVX_BOOT]
 - Searches for (hdX,2) [MVX_DATA] via filesystem label `MVX_DATA`
         │
         ▼
[Executes /boot/grub/grub.cfg]
         │
         ▼
[Sources /boot/grub/mventx_menu.cfg (Generated Menu)]
         │
         ▼
[Renders MVentX Graphical Boot Menu]
         │
         ▼
[User Selects Boot Environment]
         │
 ┌───────┴──────────────────────────────┐
 │                                      │
 ▼                                      ▼
[Type A: ISO Boot]             [Type B: Chainload]
- Mounts ISO via loopback      - Sets root to target EFI/partition
- Extracts kernel & initrd     - Invokes `chainloader /path/to/boot.efi`
- Hands over boot parameters   - Hands execution over to OS bootloader
```

---

## 2. Step-by-Step Execution Sequence

### Stage 1: UEFI Firmware Hand-Off
1. The target machine firmware iterates through its boot priority list and selects the MVentX USB drive.
2. In UEFI mode, the firmware looks for the default fallback binary:
   `/EFI/BOOT/BOOTX64.EFI` on the FAT32 boot partition (`MVX_BOOT`).
3. Execution transfers directly to the GRUB 2 standalone EFI image.

### Stage 2: GRUB 2 Initialization
1. GRUB initializes runtime drivers from its embedded core or `/boot/grub/modules/`.
2. Core modules loaded include:
   - `normal`
   - `part_gpt` and `part_msdos`
   - `fat` (for `MVX_BOOT`)
   - `exfat` (for `MVX_DATA`)
   - `search`, `test`, `echo`, `loopback`, `iso9660`
3. GRUB searches for the data partition by filesystem label:
   ```grub
   search --no-floppy --set=mventx_data_dev --label MVX_DATA
   ```

### Stage 3: Configuration & Menu Sourcing
1. GRUB locates `grub.cfg` on `MVX_BOOT`.
2. `grub.cfg` sets the visual environment (resolution, fonts, graphical theme).
3. `grub.cfg` sources the dynamic menu generated by the MVentX management engine:
   ```grub
   if [ -f ($root)/boot/grub/mventx_menu.cfg ]; then
       configfile ($root)/boot/grub/mventx_menu.cfg
   fi
   ```
4. Only items marked with `"enabled": true` in the configuration schema are rendered. Disabled environments are excluded or hidden.

### Stage 4: Payload Execution (Production Architecture)

Depending on the registered `boot_method`, GRUB executes the appropriate recipe:

#### Method A: Linux ISO (Loopback Boot)
- Loopback mount:
  ```grub
  loopback loop ($mventx_data_dev)/isos/ubuntu-22.04.iso
  linux (loop)/casper/vmlinuz boot=casper iso-scan/filename=/isos/ubuntu-22.04.iso quiet splash ---
  initrd (loop)/casper/initrd
  boot
  ```

#### Method B: Windows Setup ISO
- Uses a dual-stage or wimboot/memdisk mechanism or UEFI chainloading adapted for Windows Installation media.

#### Method C: Direct Chainloading
- Used for pre-installed operating systems, Windows Boot Manager, or secondary bootloaders:
  ```grub
  chainloader ($target_dev)/EFI/Microsoft/Boot/bootmgfw.efi
  boot
  ```

## 3. Milestone 1 Prototype Boot Behavior

In Milestone 1, the prototype establishes and verifies the core bootloader control flow without executing live operating system kernels:

1. **Host-Side Generation**: The Python generator (`core/boot_config/generator.py`) reads `mventx.json` and outputs `mventx_menu.cfg`.
2. **GRUB Boot Verification**: Upon boot, GRUB loads `grub.cfg`, sets MVentX color schemes, and loads `mventx_menu.cfg`.
3. **Environment Verification Entry**: Selecting an environment displays its verified registration metadata (display name, unique ID, boot method, ISO path, custom arguments).
4. **Fallback Handling**: If `mventx.json` is empty or all environments are disabled, a clean fallback menu entry is rendered explaining that no environments are currently enabled.
5. **Recovery Mode**: If `mventx_menu.cfg` is missing entirely, `grub.cfg` provides an informative unconfigured recovery entry.

---

## 4. Failure Modes & Fallbacks

- **Missing Data Partition**: If `MVX_DATA` cannot be found by label, GRUB falls back to searching on `$root` or prompts the user.
- **Missing or Corrupted Menu**: If `mventx_menu.cfg` is missing, `grub.cfg` renders a fallback "MVentX Recovery / Unconfigured Mode" entry.
- **Empty Registry**: If no environments are enabled, the generator renders a fallback "No environments registered or enabled" entry with clear next steps.
